Causa do pico (QA: export 36 MB ~1,27 GB, restore ~1,40 GB, base 634 MB): payload decifrado inteiro + JSON + bytes + ciphertext + base64 + arquivo-string coexistindo (e o mesmo no restore, mais o `JSON.parse` do payload). Agora: export lê o banco em lotes de 100, serializa por gravação, cifra com AES-GCM em fluxo (`cipher.update` por 192 KiB; a tag só sai no `final()`, idêntico ao one-shot) e grava o base64 por blocos num `FileHandle`; restore lê o arquivo em blocos (tag lida do fim do arquivo), decifra em fluxo, decodifica UTF-8 estrito atravessando as bordas, fatia o JSON por registro (`json-slices.ts`: só acha fronteiras; o `JSON.parse` nativo valida cada fatia; fuzz 4 000 docs contra o `JSON.parse`) e grava em lotes de 100 na transação exclusiva. Números medidos em Node/V8 (jest, `--expose-gc`, memória VIVA = heap + ArrayBuffers após GC, arquivo do harness descontado) com 1 200 / 2 400 / 4 800 gravações (7 / 14 / 28 MB de JSON): export +35 / +57 / +92 MB → +10 / +10 / +11 MB; restore +39 / +78 / +155 MB → +2 / +2 / +2–4 MB (antes cresce linear com o dado; agora é ~constante, ∝ lote). O jest também prova por fronteira que nenhum buffer/string acima de ~256 KB cruza cifra/base64/UTF-8/handle e que o `JSON.parse` do restore só vê fatias < 64 KB (28 MB de payload). **NÃO medido em aparelho/Hermes**: o RSS real (a meta < ~700 MB total, ou seja ≲ +65 MB sobre a base de 634 MB, só se confirma com `VmHWM`; roteiro em `.nexus/runs/slice-g/impl-memory.md`). [INFERÊNCIA] o GC do Hermes pode reter lixo (blocos de 192–256 KB, strings por registro) acima do conjunto vivo; se o pico ainda passar de ~700 MB, o resíduo é lixo de GC/base do app, não cópias do arquivo. Custos aceitos: (a) o export decifra cada campo 2× (os `stats` e o tamanho do JSON precisam estar no cabeçalho autenticado/AAD antes da 1ª cifra e o limite de 50 MB vale antes do KDF): ~+2 s de CPU em 36 MB, em lotes; se os dados mudarem entre os passes a exportação aborta ("Os dados mudaram durante a exportação") em vez de gravar cabeçalho incoerente; (b) o restore decifra 2× (1º passe só confirma a tag — GCM só autentica no fim — e dá `BackupPassphraseError` sem tocar no banco; 2º alimenta o parser; commit só após a tag do 2º passe); (c) a transação exclusiva fica aberta durante o parse (antes, só durante os INSERTs); (d) arquivo fora do layout do exportador (JSON reformatado/indentado, `data_b64` fora de último, cabeçalho > 4 KB) cai no caminho antigo em memória (mesmo pico de antes; funciona, só não economiza); (e) `recordings`/`customTemplates` repetidos no mesmo documento são recusados como corrompidos (o `JSON.parse` ficaria com o último); a validação de versão/app agora vem depois do documento inteiro (erro de sintaxe tem precedência) e desfaz o que já foi gravado.
